## 2. Contexto y evidencia

### 2.1 Escenario observado (E2E-B, cita 31)

1. Cita **31** creada por el flujo normal; la fila de creación C
   (`appointment.confirmed:31:v1`) guarda `calendar_event_id = 4qh5h55r8sbki6jl2927c4fb64`.
2. El evento se **borra a mano** en Google Calendar para simular «ya eliminado».
3. La cita se cancela desde la app. El backend emite `appointment.cancelled` (Spec 010) y n8n ejecuta el workflow.
4. La ejecución n8n **13** sale por la **salida de error** de `Elimina cita` (comportamiento correcto: el borrado falla).
5. El resultado persistido es incorrecto: la fila de creación queda
   `cancellation_status='failed'`, `cancellation_detail='http_error_unknown'` y
   con `calendar_event_id` **sin limpiar**.

### 2.2 Ítem real recibido por `Clasificar resultado de Calendar`

La entrada real del clasificador fue la **fila de creación** con el error como
**string**:

```json
{
  "event_id": "appointment.confirmed:31:v1", "event_version": 1,
  "event_type": "appointment.confirmed", "appointment_id": 31,
  "service": "psychology_integral", "appointment_date": "2026-11-04",
  "appointment_time": "10:00", "appointment_status": "confirmed",
  "processing_status": "completed", "occurred_at": "2026-11-02 19:24:45",
  "calendar_event_id": "4qh5h55r8sbki6jl2927c4fb64",
  "email_processing_status": null, "cancellation_status": null,
  "cancellation_detail": null,
  "id": 13, "createdAt": "2026-11-02T18:24:47.798Z",
  "updatedAt": "2026-11-02T18:24:48.443Z",
  "error": "Your request is invalid or could not be processed by the service"
}
```

No aparecen `httpCode`, `statusCode` ni `response`. El mensaje es genérico y **no
contiene el código HTTP**, por lo que tampoco puede deducirse de forma fiable del
texto.

### 2.3 Lectura

- El clasificador diseñado en `plan.md §9.5.5` lee
  `error.httpCode` → `error.statusCode` → `error.response.status`. Con este ítem,
  las tres lecturas son `undefined` y el resultado es
  `http_error_unknown`, no `not_found`.
- El estado se escribe en la fila correcta (C, la fila de creación) y con las
  columnas correctas (D3/D4), pero con un **valor falso**: el evento no existe y
  el caso debía cerrarse como `completed` + `not_found` (RF-10, D1).
- Al no reconocerse como completado, no se limpia `calendar_event_id`; un
  reintento posterior volvería a llamar a Calendar y seguiría sin poder
  clasificar el 404 → riesgo de bucle de reintentos (R5 del plan).

## 3. Causa raíz

### 3.1 Mecanismo

El nodo `Elimina cita` era `n8n-nodes-base.googleCalendar`. En su **salida de
error**, ese nodo emite el error en **formato legacy**: `error` es un **string**
con el mensaje del servicio y **no** incluye los campos estructurados
(`httpCode`, `statusCode`, `response`) que el clasificador espera. El código HTTP
**no está disponible en el ítem**, así que ninguna lectura del clasificador puede
recuperarlo.

No es un fallo del clasificador «por sí solo»: el contrato de entrada en el que
se basó el diseño (§9.5.5) no se cumple con este nodo. El clasificador hace lo
único que puede con la información recibida (`http_error_unknown`), y el efecto
es que RF-10 queda sin cumplir.

### 3.2 Por qué el diseño no lo detectó

El plan asumió que el error de Google Calendar llegaría con `httpCode` y dejó una
verificación obligatoria en T20-B (§9.5.4). Esa verificación **funcionó**: al
ejecutarla se descubrió que el campo no existe. La laguna fue de **diseño de la
fuente del error** (nodo `googleCalendar`), no de la comprobación.

## 5. Comportamiento esperado (criterios verificables)

- **CA-D007-01 (RF-10):** CUANDO el `DELETE` a Google Calendar responda **404** o
  **410**, EL SISTEMA DEBE registrar `cancellation_status='completed'` y
  `cancellation_detail='not_found'`, limpiar `calendar_event_id` y cerrar la fila
  del evento X en `completed`; nunca `failed`.
- **CA-D007-02 (RF-8):** CUANDO el borrado falle con un código HTTP disponible,
  EL SISTEMA DEBE registrar `http_error_<code>` con el código real. El motivo
  `http_error_unknown` queda reservado para cuando **no** haya código en el ítem.
- **CA-D007-03:** El nodo `Elimina cita` DEBE ser `n8n-nodes-base.googleCalendar`
  (tv 1.3, `operation: delete`) con la configuración de `plan.md §9.5.1`,
  conservando nombre, conexiones, credencial `googleCalendarOAuth2Api`,
  `onError: continueErrorOutput` y `retryOnFail: false`. *(Sustituye a la
  redacción inicial con HTTP Request, descartada por restricción de n8n Cloud;
  ver §11.1.)*
- **CA-D007-06 (RF-10, vigente):** CUANDO el borrado falle, EL SISTEMA DEBE
  verificar el evento con `events.get` (`Verificar evento`): si devuelve
  `status ∈ {cancelled, canceled}` o falla con 404, DEBE registrar `completed` /
  `not_found` y limpiar `calendar_event_id`; si devuelve el evento con otro
  estado, DEBE registrar `failed` / `http_error_unknown` conservando el id.
- **CA-D007-04:** CUANDO Google Calendar responda **2xx/204** sin cuerpo, EL
  SISTEMA DEBE obtener un ítem sin `error` → `calendar_ok: true` y
  `cancellation_detail: ''`.
- **CA-D007-05 (histórico, vigente solo en la rama de éxito):** La salvaguarda de
  `error` como string DEBE extraer un código solo si el texto contiene un 4xx/5xx
  (`\b([45]\d{2})\b`) y **nunca** inventarlo. El mensaje genérico «Your request is
  invalid or could not be processed by the service» **no** se mapea a
  `not_found`; ese caso lo resuelve CA-D007-06.

## 6. Primera corrección propuesta (opción A, 2026-11-02) — **SUPERADA**

> Esta corrección se ejecutó (JSON v2) y **falló**: n8n Cloud prohíbe la
> credencial OAuth2 de Google Calendar en nodos HTTP Request. Se conserva como
> historial de decisión; el diseño vigente es §12.2.

### 6.1 Sustitución del nodo

`Elimina cita` cambia **solo `type` y `parameters`**; conserva el **mismo nombre**
para no tocar conexiones ni expresiones:

| Parámetro | Valor |
|---|---|
| `type` | `n8n-nodes-base.httpRequest` |
| `typeVersion` | `4.2` |
| `method` | `DELETE` |
| `url` | `https://www.googleapis.com/calendar/v3/calendars/ingjazar@gmail.com/events/{{ encodeURIComponent($json.calendar_event_id) }}` |
| `authentication` | `predefinedCredentialType` |
| `nodeCredentialType` | `googleCalendarOAuth2Api` |
| `credentials` | `googleCalendarOAuth2Api` (id `Jzc9xfMvMH5AeRBN`, nombre `Google Calendar account`), sin cambios |
| `options` | `{}` |
| `sendBody` | `false` (sin `body` ni `qs`) |
| `onError` | `continueErrorOutput` |
| `retryOnFail` | `false` |

Motivo: el nodo HTTP de n8n **sí** rellena `error.httpCode` en la salida de
error, por lo que el clasificador de `plan.md §9.5.5` funciona como se diseñó.

### 6.2 Clasificador

Se mantiene la lectura actual (`error.httpCode` → `error.statusCode` →
`error.response.status`) y se añade **solo** una salvaguarda para `error` como
string: si el texto contiene un 4xx/5xx (patrón `\b([45]\d{2})\b`), se usa ese
código; si no, sigue `http_error_unknown`. No se inventan códigos ni se mapean
mensajes genéricos. `jsCode` final en `plan.md §9.5.5`.

### 6.3 Alternativa descartada

- **Mapear el mensaje genérico «Your request is invalid or could not be
  processed by the service» a `not_found`:** descartada porque enmascararía un
  **401/403 real** como «ya eliminado», marcaría `completed` una cancelación no
  realizada y perdería el `calendar_event_id` sin haber borrado nada.
- **Mantener `googleCalendar` y consultar antes si el evento existe:** más
  llamadas y latencia, y sigue dependiendo de la misma API para resolver el 404.

## 11. Actualización 2026-11-02 (ciclos 2 y 3)

### 11.1 Ciclo 2 — JSON v2 con HTTP Request: **descartado**

- Artefacto: `docs/workflows/hu-007/n8n-hu-007-integracion-citas-2026-11-02.json`
  (nodo `Elimina cita` = `n8n-nodes-base.httpRequest` 4.2, `DELETE` a la API de

- Importado y activado en n8n Cloud; ejecución real sobre la cita **32**.
- Resultado: `cancellation_status='failed'`,
  `cancellation_detail='http_error_unknown'`. El ítem de error del nodo fue:

  ```json
  "error": "This credential is configured to prevent use within an HTTP Request or GraphQL node"
  ```

- **Causa raíz:** n8n Cloud **prohíbe** usar credenciales OAuth2 de Google en
  nodos HTTP Request/GraphQL. La petición nunca llega a Google, así que no existe
  código HTTP que clasificar. No es un defecto del diseño del clasificador, sino
  una restricción de plataforma: **la opción A no es viable en este entorno**.

### 11.2 Ciclo 3 — JSON v3 con `googleCalendar` + clasificador endurecido: **insuficiente**

- Artefacto: `docs/workflows/hu-007/n8n-hu-007-integracion-citas-2026-11-02-v3.json`
  (nodo `Elimina cita` restaurado a `googleCalendar` 1.3; `jsCode` con lectura de
  `httpCode`/`statusCode`/`status`/`response.status`/`cause.*` y respaldo por
  serialización + regex de 4xx/5xx).
- Importado y activado; reenvío de `appointment.cancelled:32:v1` por la rama de
  reintento. Ejecución en **`Success`**, `Clasificar resultado de Calendar`
  ejecutado, con salida real:

  ```json
  { "calendar_ok": false, "calendar_http_code": null, "cancellation_detail": "http_error_unknown" }
  ```

- El ítem de error del nodo Calendar es:

  ```json
  "error": "Your request is invalid or could not be processed by the service"
  ```

- **Causa raíz:** el nodo `googleCalendar` de n8n **oculta el código HTTP y el
  cuerpo** de la respuesta de Google. El mensaje es genérico y no contiene
  ningún 4xx/5xx ni en campos estructurados ni serializado. **Ninguna
  interpretación del texto puede distinguir 404/410 de 400/403**, así que
  clasificar por mensaje es inviable y una heurística textual produciría falsos
  `completed`.

### 11.3 Consecuencia

RF-10 (404/410 ⇒ completado) **no es alcanzable** interpretando el error del
nodo Calendar. La vía que queda es **verificar la existencia del evento** con una
llamada independiente (`Get` del evento) tras un borrado fallido: si el `Get`
devuelve el evento, el borrado falló de verdad; si el `Get` falla, el evento ya
no está. Es un **cambio de diseño** que requiere actualizar `plan.md` y la
aprobación de la usuaria antes de implementar.

Estado del defecto: **`ABIERTO` — bloqueado a la espera de decisión de diseño**.

## 12. Corrección definitiva (JSON v5) y resultados E2E — 2026-11-04

### 12.1 Causa raíz confirmada

`events.get` **sí devuelve** un evento borrado en Google Calendar: lo devuelve con
`status: "cancelled"` hasta que se purga. Por eso:

1. el `delete` falla (Google responde 410/404, que n8n oculta), y
2. la verificación de mera existencia (v4) concluía «sigue existiendo».

El discriminador correcto es el **estado del evento**, no su existencia.

### 12.2 Diseño aplicado (v5, 48 nodos)

```text
Elimina cita (delete)
├── éxito            -> Clasificar -> ¿Borrado o ya eliminado? -> completed / detalle vacío
└── error            -> Verificar evento (get)
     ├── status cancelled/canceled -> Preparar no encontrado -> completed / not_found / id vacío
     ├── status otro (confirmed...) -> Preparar borrado fallido -> failed / http_error_unknown
     └── error (404 puro)          -> Preparar no encontrado -> completed / not_found / id vacío
```

Artefacto: `docs/workflows/hu-007/n8n-hu-007-integracion-citas-2026-11-02-v5.json`
(sha256 `8918306709c0e13132861cea04cc2d7ff98dded6d7f005c94e4f5e02f3dfb766`).

### 12.4 Riesgos residuales

- **R6**: si `Verificar evento` fallara por red o credencial, se registraría
  `not_found` (falso positivo). Mitigación: el borrado exitoso no pasa por la
  verificación y la credencial ya se usa para crear eventos en el mismo flujo.
- Un evento cancelado permanece accesible por API hasta su purga; el flujo lo
  trata como «ya no existe», que es el comportamiento requerido por RF-10.
